# PRD-AUTH: การลงทะเบียนและการยืนยันตัวตน

## 1. ภาพรวม

ลูกค้าสมัครสมาชิกด้วยตนเองได้ ส่วนบัญชีของเจ้าหน้าที่ ผู้จัดการ และผู้ดูแลระบบ เป็นบัญชีที่ระบบจัดเตรียมไว้ล่วงหน้า การเข้าสู่ระบบใช้ชื่อผู้ใช้ (username) และรหัสผ่าน ระบบออกโทเคนเข้าสู่ระบบให้ใช้แนบกับทุกคำขอที่ต้องยืนยันตัวตน

## 2. ขอบเขต

**อยู่ในขอบเขต:** การลงทะเบียนของลูกค้า การเข้าสู่ระบบ การล็อกชั่วคราวจากการเข้าสู่ระบบผิดซ้ำ อายุของโทเคน การออกจากระบบ การเปลี่ยนรหัสผ่าน การบังคับเปลี่ยนรหัสผ่านหลังผู้ดูแลระบบรีเซ็ต และการนำผู้ใช้ไปยังหน้าที่เหมาะสมตามบทบาท

**อยู่นอกขอบเขต:** การลืมรหัสผ่านด้วยตนเอง (self-service reset) การยืนยันอีเมลหรือเบอร์โทร การยืนยันตัวตนหลายปัจจัย และการเข้าสู่ระบบผ่านบริการภายนอก

## 3. ข้อกำหนด

### REQ-AUTH-001: การลงทะเบียนของลูกค้า

หน้า `/register` และ `POST /api/auth/register` ต้องรองรับการสมัครสมาชิก โดยมีกฎดังนี้

| ฟิลด์ | กฎ |
|---|---|
| `username` | จำเป็น ยาว 4 ถึง 20 อักขระ ประกอบด้วยตัวอักษร `A-Z` `a-z` ตัวเลข `0-9` และขีดล่าง `_` เท่านั้น |
| `password` | จำเป็น ยาว 8 ถึง 20 อักขระ ห้ามมีช่องว่าง ต้องมีตัวอักษรละติน (`A-Z` หรือ `a-z`) อย่างน้อย 1 ตัว และตัวเลขอย่างน้อย 1 ตัว |
| `display_name` | จำเป็น ยาว 2 ถึง 50 อักขระ (หลังตัดช่องว่างหน้า-หลัง) |
| `birthdate` | จำเป็น รูปแบบ `YYYY-MM-DD` เป็นวันที่ที่มีอยู่จริง ไม่ใช่วันในอนาคต ไม่ก่อน `1900-01-01` และผู้สมัครต้องมีอายุครบ 18 ปีบริบูรณ์ |

- การคำนวณอายุอ้างอิงวันที่ปัจจุบันตามเวลาประเทศไทย ผู้สมัครมีอายุครบ 18 ปีเมื่อวันที่ปัจจุบันเป็นวันเกิดครบ 18 ปีหรือหลังจากนั้น ผู้ที่เกิดวันที่ 29 กุมภาพันธ์ ให้ถือวันเกิดครบปีในปีที่ไม่ใช่ปีอธิกสุรทินเป็นวันที่ 1 มีนาคม
- ช่อง "ยืนยันรหัสผ่าน" (`confirm_password`) ตรวจสอบที่หน้าจอเท่านั้น API ไม่ต้องรับค่านี้
- บัญชีที่สร้างต้องมีบทบาท `customer` เสมอ ฟิลด์ `role` หรือฟิลด์อื่นที่ไม่ได้ระบุซึ่งส่งมาในคำขอต้องถูกละเว้น
- เมื่อสำเร็จ ระบบตอบ 201 พร้อมเนื้อหา `id`, `username`, `display_name`, `role`, `created_at` โดยไม่มีข้อมูลเกี่ยวกับรหัสผ่าน และ **ไม่** เข้าสู่ระบบให้อัตโนมัติ หน้าจอนำผู้ใช้ไปยังหน้า Sign in พร้อมข้อความแจ้งความสำเร็จ
- บัญชีใหม่ไม่มีที่อยู่ ไม่มีคำสั่งซื้อ ตะกร้าว่าง และไม่มีรายการโปรด
- ชื่อผู้ใช้เก็บตามตัวพิมพ์ที่ผู้สมัครป้อน (หลังตัดช่องว่าง)

**เกณฑ์การตรวจรับ**

| ID | Given | When | Then |
|---|---|---|---|
| AC-AUTH-001.1 | ไม่มีบัญชี `newbuyer1` | สมัครด้วย `newbuyer1` / `Passw0rdA` / `New Buyer` / `1999-05-20` | ได้ 201 บทบาทเป็น `customer` และไม่ได้โทเคน |
| AC-AUTH-001.2 | เหมือนข้างต้น | ส่งคำขอสมัครที่มี `"role":"admin"` เพิ่ม | ได้ 201 และบัญชีที่ได้มีบทบาท `customer` |
| AC-AUTH-001.3 | เหมือนข้างต้น | สมัครด้วยรหัสผ่าน `Password` (ไม่มีตัวเลข) | ได้ 400 `VALIDATION_ERROR` และ `details` ชี้ฟิลด์ `password` |
| AC-AUTH-001.4 | ไม่มี | สมัครด้วยวันเกิดที่ทำให้ผู้สมัครอายุ 17 ปี | ได้ 400 `VALIDATION_ERROR` และ `details` ชี้ฟิลด์ `birthdate` |

### REQ-AUTH-002: ความไม่ซ้ำของชื่อผู้ใช้

- ชื่อผู้ใช้ต้องไม่ซ้ำกันโดยไม่แยกตัวพิมพ์ใหญ่-เล็ก (`Customer1` ถือว่าซ้ำกับ `customer1`)
- ความไม่ซ้ำต้องถูกบังคับที่ระดับฐานข้อมูล
- เมื่อชื่อซ้ำ ระบบต้องตอบ 409 `USERNAME_TAKEN`
- หากมีคำขอสมัครด้วยชื่อเดียวกันเข้ามาพร้อมกัน ต้องสำเร็จเพียงรายการเดียว รายการที่เหลือได้ 409

**เกณฑ์การตรวจรับ**

| ID | Given | When | Then |
|---|---|---|---|
| AC-AUTH-002.1 | มีบัญชี `customer1` | สมัครด้วยชื่อ `CUSTOMER1` | ได้ 409 `USERNAME_TAKEN` |

### REQ-AUTH-003: การเข้าสู่ระบบ

`POST /api/auth/login` รับ `username` และ `password`

- ชื่อผู้ใช้ถูกตัดช่องว่างหน้า-หลังและเปรียบเทียบโดยไม่แยกตัวพิมพ์ใหญ่-เล็ก ส่วนรหัสผ่านเปรียบเทียบโดยแยกตัวพิมพ์ใหญ่-เล็ก
- หากฟิลด์ใดว่างหรือขาด ต้องตอบ 400 `VALIDATION_ERROR` (ไม่ใช่ 401)
- ลำดับการพิจารณาเมื่อฟิลด์ครบถ้วน
  1. ไม่พบชื่อผู้ใช้ → 401 `INVALID_CREDENTIALS`
  2. บัญชีถูกล็อกชั่วคราวและยังไม่ถึงเวลาปลดล็อก → 423 `ACCOUNT_LOCKED` (ตาม `REQ-AUTH-004`)
  3. รหัสผ่านไม่ถูกต้อง → 401 `INVALID_CREDENTIALS` และนับเป็นการเข้าสู่ระบบผิด
  4. บัญชีถูกล็อกโดยผู้ดูแลระบบ → 403 `ACCOUNT_DISABLED` (ตาม `REQ-AUTH-005`)
  5. สำเร็จ
- กรณีไม่พบชื่อผู้ใช้และกรณีรหัสผ่านผิด ต้องตอบรหัสสถานะ รหัสข้อผิดพลาด และข้อความเหมือนกันทุกประการ (`Invalid username or password.`) เพื่อไม่เปิดเผยว่ามีชื่อผู้ใช้นั้นในระบบ
- เมื่อสำเร็จ ตอบ 200 พร้อมเนื้อหา:
  ```json
  {
    "token": "<โทเคน>",
    "token_type": "Bearer",
    "expires_in": 600,
    "must_change_password": false,
    "user": { "id": 1, "username": "customer1", "display_name": "Somchai Jaidee", "role": "customer" }
  }
  ```

**เกณฑ์การตรวจรับ**

| ID | Given | When | Then |
|---|---|---|---|
| AC-AUTH-003.1 | มีบัญชี `customer1` | เข้าสู่ระบบด้วย `CUSTOMER1` และรหัสผ่านที่ถูกต้อง | ได้ 200 และ `user.role` เป็น `customer` |
| AC-AUTH-003.2 | ไม่มี | เข้าสู่ระบบด้วยชื่อผู้ใช้ที่ไม่มีอยู่ | ได้ 401 `INVALID_CREDENTIALS` ข้อความ `Invalid username or password.` |
| AC-AUTH-003.3 | มีบัญชี `customer1` | เข้าสู่ระบบด้วยรหัสผ่านผิด | ได้ 401 `INVALID_CREDENTIALS` ข้อความเหมือนกรณีก่อนหน้า |
| AC-AUTH-003.4 | ไม่มี | ส่งคำขอเข้าสู่ระบบโดยไม่มี `password` | ได้ 400 `VALIDATION_ERROR` |

### REQ-AUTH-004: การล็อกชั่วคราวจากการเข้าสู่ระบบผิดซ้ำ

- ระบบต้องนับจำนวนครั้งที่เข้าสู่ระบบผิด (ชื่อผู้ใช้มีอยู่ แต่รหัสผ่านไม่ถูกต้อง) ต่อเนื่องกันของแต่ละบัญชี
- เมื่อเข้าสู่ระบบผิดครบ 5 ครั้งติดต่อกัน ระบบต้องล็อกบัญชีชั่วคราวเป็นเวลา **3 นาที** นับจากเวลาที่เกิดการผิดครั้งที่ 5 โดยการผิดครั้งที่ 1 ถึง 5 ตอบ 401 `INVALID_CREDENTIALS` ตามปกติ
- ระหว่างที่ถูกล็อกชั่วคราว ทุกคำขอเข้าสู่ระบบของบัญชีนั้น (แม้รหัสผ่านถูกต้อง) ต้องตอบ 423 `ACCOUNT_LOCKED` ข้อความ `Your account is temporarily locked. Please try again in {n} minute(s).` โดย `{n}` คือเวลาที่เหลือเป็นนาที ปัดขึ้น และไม่ต่ำกว่า 1 คำขอที่ถูกปฏิเสธเหล่านี้ต้องไม่เปลี่ยนตัวนับและไม่ต่อเวลาล็อก
- เมื่อพ้นเวลาล็อก ระบบต้องให้เข้าสู่ระบบได้ และตัวนับกลับเป็น 0
- การเข้าสู่ระบบสำเร็จต้องรีเซ็ตตัวนับเป็น 0
- การล็อกชั่วคราวมีผลกับการเข้าสู่ระบบครั้งใหม่เท่านั้น โทเคนที่ออกไปแล้วยังใช้ได้
- การพยายามเข้าสู่ระบบด้วยชื่อผู้ใช้ที่ไม่มีอยู่ ไม่ทำให้เกิดการล็อกใด ๆ

**เกณฑ์การตรวจรับ**

| ID | Given | When | Then |
|---|---|---|---|
| AC-AUTH-004.1 | บัญชี `customer3` ยังไม่เคยเข้าสู่ระบบผิด | เข้าสู่ระบบผิด 5 ครั้งติดกัน แล้วลองอีกครั้งด้วยรหัสผ่านที่ถูกต้อง | ครั้งที่ 1 ถึง 5 ได้ 401 ครั้งที่ 6 ได้ 423 `ACCOUNT_LOCKED` |
| AC-AUTH-004.2 | บัญชีถูกล็อกชั่วคราวแล้ว | รอให้ครบ 3 นาที แล้วเข้าสู่ระบบด้วยรหัสผ่านที่ถูกต้อง | ได้ 200 |
| AC-AUTH-004.3 | บัญชีเข้าสู่ระบบผิดมาแล้ว 4 ครั้ง | เข้าสู่ระบบสำเร็จ แล้วเข้าสู่ระบบผิดอีก 4 ครั้ง | ไม่ถูกล็อก (ตัวนับเริ่มใหม่หลังสำเร็จ) |

### REQ-AUTH-005: บัญชีที่ถูกล็อกโดยผู้ดูแลระบบ

- เมื่อบัญชีมีสถานะ `LOCKED` (ล็อกโดยผู้ดูแลระบบตาม `REQ-ADM-002`) และผู้ใช้ป้อนรหัสผ่านถูกต้อง ระบบต้องปฏิเสธด้วย 403 `ACCOUNT_DISABLED` ข้อความ `Your account has been locked by an administrator.`
- การปฏิเสธนี้ไม่ใช้ตัวนับและกำหนดเวลาของ `REQ-AUTH-004`

**เกณฑ์การตรวจรับ**

| ID | Given | When | Then |
|---|---|---|---|
| AC-AUTH-005.1 | ผู้ดูแลระบบล็อกบัญชี `customer1` | เข้าสู่ระบบด้วยรหัสผ่านที่ถูกต้อง | ได้ 403 `ACCOUNT_DISABLED` |

### REQ-AUTH-006: โทเคนเข้าสู่ระบบ

- โทเคนเป็นสตริงสุ่มที่คาดเดาไม่ได้ ยาวไม่น้อยกว่า 32 อักขระ
- ผู้ใช้ส่งโทเคนในส่วนหัว `Authorization: Bearer <โทเคน>`
- โทเคนมีอายุ **10 นาที (600 วินาที)** นับจากเวลาที่ออก เป็นอายุแบบตายตัว การใช้งานโทเคนไม่ทำให้อายุขยายออกไป
- โทเคนที่หมดอายุ ไม่ถูกต้อง หรือส่วนหัวรูปแบบผิด ต้องตอบ 401 `UNAUTHENTICATED`
- การเข้าสู่ระบบแต่ละครั้งออกโทเคนใหม่ ผู้ใช้หนึ่งคนมีโทเคนที่ใช้งานได้พร้อมกันหลายใบ

**เกณฑ์การตรวจรับ**

| ID | Given | When | Then |
|---|---|---|---|
| AC-AUTH-006.1 | ผู้ใช้เข้าสู่ระบบสำเร็จ | เรียก `GET /api/me` ด้วยโทเคนภายใน 10 นาที | ได้ 200 |
| AC-AUTH-006.2 | ผู้ใช้เข้าสู่ระบบมาแล้วเกิน 10 นาที | เรียก `GET /api/me` ด้วยโทเคนเดิม | ได้ 401 `UNAUTHENTICATED` |
| AC-AUTH-006.3 | ผู้ใช้เข้าสู่ระบบสำเร็จ | เรียก `GET /api/me` โดยส่วนหัวเป็น `Authorization: Token abc` | ได้ 401 `UNAUTHENTICATED` |

### REQ-AUTH-007: การออกจากระบบ

- `POST /api/auth/logout` ต้องทำให้โทเคนที่ใช้เรียกใช้ไม่ได้ทันที และตอบ 204
- โทเคนอื่นของบัญชีเดียวกันไม่ได้รับผลกระทบ
- การเรียกใช้ API ด้วยโทเคนที่ออกจากระบบไปแล้วต้องได้ 401 `UNAUTHENTICATED`
- เมื่อออกจากระบบบนหน้าจอ ระบบต้องล้างโทเคนที่เก็บไว้และนำผู้ใช้ไปหน้า Sign in

**เกณฑ์การตรวจรับ**

| ID | Given | When | Then |
|---|---|---|---|
| AC-AUTH-007.1 | ผู้ใช้เข้าสู่ระบบสำเร็จ | ออกจากระบบ แล้วเรียก `GET /api/me` ด้วยโทเคนเดิม | ออกจากระบบได้ 204 และ `GET /api/me` ได้ 401 |

### REQ-AUTH-008: การเปลี่ยนรหัสผ่าน

`POST /api/auth/change-password` รับ `current_password` และ `new_password`

- ลำดับการพิจารณา
  1. ตรวจรูปแบบของคำขอ: ทั้งสองฟิลด์จำเป็น และ `new_password` ต้องเป็นไปตามกฎรหัสผ่านใน `REQ-AUTH-001` มิฉะนั้นตอบ 400 `VALIDATION_ERROR`
  2. `current_password` ต้องตรงกับรหัสผ่านปัจจุบัน มิฉะนั้นตอบ 400 `INVALID_CURRENT_PASSWORD`
  3. `new_password` ต้องไม่ซ้ำกับรหัสผ่านปัจจุบัน มิฉะนั้นตอบ 400 `VALIDATION_ERROR` โดย `details` ชี้ฟิลด์ `new_password`
- เมื่อสำเร็จ ตอบ 204 รหัสผ่านใหม่มีผลทันที โทเคนอื่นทั้งหมดของบัญชีนั้นใช้ไม่ได้ทันที (ตาม `REQ-CROSS-007`) ส่วนโทเคนที่ใช้เรียกยังใช้ได้
- เมื่อสำเร็จ สถานะ "ต้องเปลี่ยนรหัสผ่าน" (ถ้ามี) ถูกยกเลิก

**เกณฑ์การตรวจรับ**

| ID | Given | When | Then |
|---|---|---|---|
| AC-AUTH-008.1 | ผู้ใช้มีโทเคน A และ B | ใช้โทเคน A เปลี่ยนรหัสผ่านสำเร็จ แล้วเรียก `GET /api/me` ด้วยโทเคน B | เปลี่ยนรหัสผ่านได้ 204 และโทเคน B ได้ 401 ส่วนโทเคน A ยังได้ 200 |
| AC-AUTH-008.2 | ผู้ใช้ล็อกอินแล้ว | ส่ง `current_password` ที่ไม่ถูกต้อง | ได้ 400 `INVALID_CURRENT_PASSWORD` |

### REQ-AUTH-009: การบังคับเปลี่ยนรหัสผ่านหลังผู้ดูแลระบบรีเซ็ต

- บัญชีที่ผู้ดูแลระบบรีเซ็ตรหัสผ่านให้ (ตาม `REQ-ADM-004`) มีสถานะ "ต้องเปลี่ยนรหัสผ่าน" จนกว่าจะเปลี่ยนรหัสผ่านสำเร็จ
- การเข้าสู่ระบบด้วยรหัสผ่านชั่วคราวสำเร็จ และตอบ `must_change_password` เป็น `true`
- ขณะอยู่ในสถานะนี้ ผู้ใช้เรียกได้เฉพาะ `GET /api/me`, `POST /api/auth/change-password` และ `POST /api/auth/logout` ส่วนคำขออื่นต้องตอบ 403 `PASSWORD_CHANGE_REQUIRED`
- หน้าจอต้องนำผู้ใช้ไปยังหน้า `/change-password` ทันทีหลังเข้าสู่ระบบ และไม่ให้เข้าหน้าอื่นจนกว่าจะเปลี่ยนรหัสผ่านสำเร็จ

**เกณฑ์การตรวจรับ**

| ID | Given | When | Then |
|---|---|---|---|
| AC-AUTH-009.1 | บัญชีมีสถานะต้องเปลี่ยนรหัสผ่าน และผู้ใช้เข้าสู่ระบบแล้ว | เรียก `GET /api/products` | ได้ 403 `PASSWORD_CHANGE_REQUIRED` |

### REQ-AUTH-010: การเข้าถึงหน้าและ API ที่ต้องยืนยันตัวตน

- ผู้ที่ยังไม่เข้าสู่ระบบที่เปิดหน้าใดก็ตามนอกจาก `/login` และ `/register` ต้องถูกนำไปหน้า `/login`
- ผู้ที่เข้าสู่ระบบแล้วแต่เปิดหน้าที่บทบาทของตนไม่มีสิทธิ์ ต้องเห็นหน้า 403 และเมนูต้องแสดงเฉพาะหน้าที่เข้าได้ตาม `docs/design/rbac-matrix.md`
- เมื่อโทเคนหมดอายุขณะใช้งานหน้าจอ ระบบต้องนำผู้ใช้ไปหน้า `/login` พร้อมข้อความ `Your session has expired. Please sign in again.`

### REQ-AUTH-011: หน้าแรกหลังเข้าสู่ระบบ

| บทบาท | หน้าแรก |
|---|---|
| `customer` | `/products` |
| `staff` | `/staff/orders` |
| `manager` | `/manager/reports` |
| `admin` | `/admin/users` |

ผู้ที่เข้าสู่ระบบแล้วเปิดหน้า `/login` หรือ `/register` ต้องถูกนำไปหน้าแรกของบทบาทตนเอง

## 4. สมมติฐาน

- บัญชีที่ระบบจัดเตรียมไว้และรหัสผ่านทดสอบระบุใน `docs/instructions/test-accounts-and-seed-data.md`
- ผู้ใช้ที่ไม่ใช่ `customer` ไม่มีบัญชีที่สร้างได้ผ่านหน้า `/register`
