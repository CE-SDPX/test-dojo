# PRD-COMMON: มาตรฐานพื้นฐานของระบบ

## 1. ภาพรวม

เอกสารฉบับนี้กำหนดมาตรฐานพื้นฐานที่ใช้กับทุกฟีเจอร์ของ DojoMart ได้แก่ รหัสสถานะ HTTP รูปแบบข้อผิดพลาด การตรวจสอบข้อมูลนำเข้า ความปลอดภัยเบื้องต้น และความสอดคล้องของข้อมูล พฤติกรรมของระบบที่ขัดกับข้อกำหนดในเอกสารนี้ ถือว่าไม่เป็นไปตามข้อกำหนด

## 2. ขอบเขต

**อยู่ในขอบเขต:** ข้อกำหนดในหัวข้อที่ 3 ทั้งหมด

**อยู่นอกขอบเขต (ไม่ถือเป็นข้อบกพร่อง):**
- นโยบาย CORS: API อนุญาตทุก origin
- จุดเชื่อมต่อสำหรับการฝึก ได้แก่ `GET /api/health`, `GET /api/version` และ `POST /api/reset` ซึ่งไม่ต้องยืนยันตัวตน
- ประสิทธิภาพ ความเร็วในการตอบสนอง และความสามารถในการรองรับผู้ใช้จำนวนมาก
- การบันทึกเหตุการณ์ (logging) และการเฝ้าระวัง (monitoring)
- การส่งอีเมลหรือการแจ้งเตือนภายนอก

## 3. ข้อกำหนด

### REQ-COM-001: รหัสสถานะ HTTP

ระบบต้องตอบรหัสสถานะ HTTP ตามตารางต่อไปนี้

| สถานการณ์ | รหัส |
|---|---|
| ดำเนินการสำเร็จและมีเนื้อหาตอบกลับ (รวมการดึงข้อมูล การแก้ไข และการดำเนินการที่คืนข้อมูล) | 200 |
| สร้างทรัพยากรใหม่สำเร็จ | 201 |
| ดำเนินการสำเร็จและไม่มีเนื้อหาตอบกลับ | 204 |
| คำขอไม่ถูกต้อง: JSON เสียหาย ข้อมูลไม่ผ่านการตรวจสอบ หรือพารามิเตอร์ query ไม่ถูกต้อง | 400 |
| ไม่ได้ยืนยันตัวตน โทเคนไม่ถูกต้องหรือหมดอายุ หรือข้อมูลเข้าสู่ระบบไม่ถูกต้อง | 401 |
| ยืนยันตัวตนแล้วแต่ไม่มีสิทธิ์ทำรายการ | 403 |
| ไม่พบทรัพยากร หรือทรัพยากรเป็นของผู้อื่นเมื่อผู้เรียกเป็น `customer` | 404 |
| วิธี HTTP ไม่รองรับสำหรับเส้นทางนั้น | 405 |
| ขัดแย้งกับสถานะปัจจุบันของข้อมูลหรือกฎธุรกิจ | 409 |
| บัญชีถูกล็อกชั่วคราวจากการเข้าสู่ระบบผิดซ้ำ | 423 |
| ข้อผิดพลาดที่ไม่คาดคิดภายในระบบ | 500 |

รหัส 500 ต้องไม่เกิดจากข้อมูลนำเข้าของผู้ใช้ ข้อมูลนำเข้าที่ไม่ถูกต้องทุกกรณีต้องได้รหัส 4xx ที่เหมาะสม

**เกณฑ์การตรวจรับ**

| ID | Given | When | Then |
|---|---|---|---|
| AC-COM-001.1 | ผู้ใช้ล็อกอินแล้ว | ส่ง `POST /api/cart/items` โดย `quantity` เป็น `"abc"` | ได้รหัส 400 และ `error.code` เป็น `VALIDATION_ERROR` |
| AC-COM-001.2 | ผู้ใช้สร้างที่อยู่สำเร็จ | ตรวจรหัสสถานะ | ได้รหัส 201 |

### REQ-COM-002: รูปแบบข้อผิดพลาด

- ทุกการตอบกลับที่เป็นข้อผิดพลาด (รหัส 4xx และ 5xx) ต้องมีเนื้อหา JSON รูปแบบเดียวกัน:
  ```json
  {
    "error": {
      "code": "VALIDATION_ERROR",
      "message": "One or more fields are invalid.",
      "details": [ { "field": "quantity", "message": "Quantity must be a whole number from 1 to 10." } ]
    }
  }
  ```
- `code` เป็นรหัสข้อผิดพลาดตามที่กำหนดใน `docs/design/api.md` หัวข้อ "รหัสข้อผิดพลาด" และ `message` เป็นข้อความภาษาอังกฤษตามตารางเดียวกัน
- `details` ปรากฏเฉพาะเมื่อ `code` เป็น `VALIDATION_ERROR` และต้องรายงานทุกฟิลด์ที่ไม่ผ่านการตรวจสอบในคำขอเดียว ไม่รายงานเฉพาะฟิลด์แรก
- เส้นทางที่ไม่มีอยู่ต้องตอบ 404 ด้วยรหัส `NOT_FOUND` ในรูปแบบเดียวกัน

**เกณฑ์การตรวจรับ**

| ID | Given | When | Then |
|---|---|---|---|
| AC-COM-002.1 | ผู้ใช้ล็อกอินแล้ว | เรียก `GET /api/no-such-path` | ได้ 404 และเนื้อหามีรูปแบบ `error.code = NOT_FOUND` |
| AC-COM-002.2 | ผู้ใช้กรอกชื่อและเบอร์โทรผิดทั้งสองฟิลด์ใน `PUT /api/me` | ส่งคำขอ | `details` มีรายการของทั้งสองฟิลด์ |

### REQ-COM-003: การตรวจสอบข้อมูลนำเข้า

1. ฟิลด์ข้อความทุกฟิลด์ต้องถูกตัดช่องว่างหน้า-หลัง (trim) ก่อนตรวจสอบและก่อนจัดเก็บ ยกเว้นรหัสผ่านซึ่งไม่ตัดช่องว่างแต่ไม่อนุญาตให้มีช่องว่าง
2. ฟิลด์ที่จำเป็นต้องมีค่า และไม่ว่างเปล่าหลังตัดช่องว่าง
3. ความยาวต้องอยู่ในช่วงที่ระบุในแต่ละข้อกำหนด โดยนับเป็นจำนวนอักขระ (character) ไม่ใช่จำนวนไบต์
4. ชนิดข้อมูลต้องตรงกับที่กำหนด: ฟิลด์จำนวนเต็มต้องรับเฉพาะจำนวนเต็ม (ไม่รับทศนิยม สตริง หรือค่า `null`) ฟิลด์จำนวนเงินต้องเป็นสตริงทศนิยมไม่เกิน 2 ตำแหน่ง
5. ฟิลด์ที่ไม่ได้ระบุในข้อกำหนดของ endpoint ต้องถูกละเว้นและต้องไม่มีผลต่อข้อมูลในระบบ (รวมถึงฟิลด์ที่ผู้ใช้พยายามส่งมาเพื่อกำหนดค่าที่ระบบเป็นผู้กำหนด เช่น `role` และ `id`)
6. ระบบต้องตรวจสอบข้อมูลที่ฝั่ง API เสมอ แม้หน้าจอ (UI) จะตรวจสอบก่อนส่งแล้ว
7. ข้อความของข้อผิดพลาดรายฟิลด์เป็นไปตามตารางใน `docs/design/api.md`

**เกณฑ์การตรวจรับ**

| ID | Given | When | Then |
|---|---|---|---|
| AC-COM-003.1 | ผู้ใช้ล็อกอินแล้ว | บันทึกชื่อแสดงผลเป็น `"  Bob  "` | ระบบจัดเก็บและแสดงเป็น `Bob` |
| AC-COM-003.2 | ผู้ใช้ล็อกอินแล้ว | ส่งชื่อแสดงผลเป็นช่องว่างล้วน | ได้ 400 `VALIDATION_ERROR` |
| AC-COM-003.3 | ผู้ใช้ล็อกอินแล้ว | ส่ง `quantity` เป็น `2.5` | ได้ 400 `VALIDATION_ERROR` |

### REQ-COM-004: การเก็บและเปิดเผยรหัสผ่านและโทเคน

- รหัสผ่านต้องถูกจัดเก็บเป็นค่าแฮชแบบเติม salt ห้ามจัดเก็บเป็นข้อความตรง
- รหัสผ่านและค่าแฮชต้องไม่ปรากฏในเนื้อหาตอบกลับของ endpoint ใดทั้งสิ้น
- โทเคนเข้าสู่ระบบปรากฏในเนื้อหาตอบกลับเฉพาะ `POST /api/auth/login`
- รหัสผ่านชั่วคราวปรากฏเฉพาะในเนื้อหาตอบกลับของ `POST /api/admin/users/{id}/reset-password`

**เกณฑ์การตรวจรับ**

| ID | Given | When | Then |
|---|---|---|---|
| AC-COM-004.1 | ผู้ใช้ล็อกอินแล้ว | เรียก `GET /api/me` | เนื้อหาไม่มีฟิลด์ที่เกี่ยวกับรหัสผ่านหรือแฮช |
| AC-COM-004.2 | มีผู้ใช้สมัครใหม่ | ตรวจตาราง `users` ในฐานข้อมูล | คอลัมน์รหัสผ่านไม่ใช่ข้อความรหัสผ่านที่ผู้ใช้ตั้ง |

### REQ-COM-005: การป้องกัน Cross-Site Scripting (XSS)

ข้อความทุกชนิดที่ผู้ใช้ป้อน (เช่น ชื่อแสดงผล ชื่อผู้รับ ที่อยู่ ความคิดเห็นรีวิว ชื่อสินค้าที่ผู้จัดการป้อน คำค้นที่แสดงซ้ำในข้อความ) ต้องถูกแสดงบนหน้าจอเป็นข้อความธรรมดา ห้ามตีความเป็น HTML หรือสคริปต์

**เกณฑ์การตรวจรับ**

| ID | Given | When | Then |
|---|---|---|---|
| AC-COM-005.1 | ลูกค้าตั้งชื่อแสดงผลเป็น `<b>x</b>` | เปิดหน้าใดก็ตามที่แสดงชื่อ | หน้าจอแสดงข้อความ `<b>x</b>` ตามตัวอักษร ไม่เป็นตัวหนา |

### REQ-COM-006: การป้องกัน SQL Injection

- ข้อมูลนำเข้าทุกชนิดต้องถูกจัดการเป็นข้อมูล ไม่มีผลต่อโครงสร้างของคำสั่งฐานข้อมูล
- ตัวอักษร `'`, `"`, `\`, `%` และ `_` ในช่องค้นหาและช่องข้อมูลอื่นต้องถูกตีความเป็นตัวอักษรธรรมดา โดยเฉพาะ `%` และ `_` ไม่ทำหน้าที่เป็นตัวแทนอักขระ

**เกณฑ์การตรวจรับ**

| ID | Given | When | Then |
|---|---|---|---|
| AC-COM-006.1 | ลูกค้าอยู่ที่หน้า Products | ค้นหาด้วยข้อความ `' OR 1=1 --` | ระบบแสดงผลการค้นหาปกติของข้อความดังกล่าว (ไม่พบสินค้า) และไม่เกิดข้อผิดพลาด |

### REQ-COM-007: การบังคับใช้สิทธิ์ที่ฝั่งเซิร์ฟเวอร์

ทุก endpoint ที่กำหนดว่าต้องยืนยันตัวตนต้องตรวจโทเคนและบทบาทที่ API เสมอ โดยไม่พึ่งการซ่อนปุ่มหรือเมนูบนหน้าจอ และต้องตรวจตามลำดับต่อไปนี้ เมื่อพบข้อผิดพลาดแรกให้ตอบทันที

| ลำดับ | การตรวจสอบ | ผลเมื่อไม่ผ่าน |
|---|---|---|
| 1 | โทเคนมีอยู่ ถูกต้อง และไม่หมดอายุ | 401 `UNAUTHENTICATED` |
| 2 | ผู้ใช้ไม่อยู่ในสถานะต้องเปลี่ยนรหัสผ่าน (ยกเว้น endpoint ที่ `REQ-AUTH-009` อนุญาต) | 403 `PASSWORD_CHANGE_REQUIRED` |
| 3 | บทบาทของผู้ใช้ได้รับอนุญาตสำหรับ endpoint ตาม `docs/design/rbac-matrix.md` | 403 `FORBIDDEN` |
| 4 | ทรัพยากรที่ระบุในเส้นทางมีอยู่และผู้เรียกมีสิทธิ์เห็น | 404 `NOT_FOUND` |
| 5 | ข้อมูลในคำขอถูกต้อง | 400 `VALIDATION_ERROR` |
| 6 | สถานะและเงื่อนไขทางธุรกิจเอื้อให้ดำเนินการ | 409 (รหัสตามกรณี) |

**เกณฑ์การตรวจรับ**

| ID | Given | When | Then |
|---|---|---|---|
| AC-COM-007.1 | ไม่มีโทเคน | เรียก `GET /api/me` | ได้ 401 |
| AC-COM-007.2 | ลูกค้าล็อกอินแล้ว | เรียก `GET /api/admin/users` โดยตรง | ได้ 403 `FORBIDDEN` |
| AC-COM-007.3 | ลูกค้าล็อกอินแล้ว | เรียก `PATCH /api/manage/orders/999999/status` โดยส่งข้อมูลผิดรูปแบบ | ได้ 403 `FORBIDDEN` (ตรวจสิทธิ์ก่อนตรวจข้อมูล) |

### REQ-COM-008: ความเป็นเจ้าของข้อมูล

- ผู้ใช้บทบาท `customer` ต้องเข้าถึงได้เฉพาะข้อมูลของตนเอง ได้แก่ โปรไฟล์ ที่อยู่ ตะกร้า รายการโปรด และคำสั่งซื้อ
- เมื่อ `customer` ระบุรหัสทรัพยากรที่เป็นของผู้อื่น ระบบต้องตอบ 404 `NOT_FOUND` เช่นเดียวกับกรณีที่ไม่มีทรัพยากรนั้น (ไม่เปิดเผยว่าทรัพยากรมีอยู่)

**เกณฑ์การตรวจรับ**

| ID | Given | When | Then |
|---|---|---|---|
| AC-COM-008.1 | `customer1` ล็อกอินแล้ว และคำสั่งซื้อรหัส 1 เป็นของ `customer2` | เรียก `GET /api/orders/1` | ได้ 404 |

### REQ-COM-009: ไม่เปิดเผยข้อมูลภายในระบบ

- ข้อผิดพลาดรหัส 5xx ต้องมีข้อความ `An unexpected error occurred.` เท่านั้น
- เนื้อหาตอบกลับต้องไม่มี stack trace, คำสั่ง SQL, เส้นทางไฟล์, ชื่อตารางหรือคอลัมน์ในฐานข้อมูล, และข้อความข้อผิดพลาดดิบของไลบรารี

### REQ-COM-010: ชนิดเนื้อหา (Content-Type)

- การตอบกลับ JSON ทุกครั้งต้องมีส่วนหัว `Content-Type: application/json; charset=utf-8`
- การตอบกลับไฟล์ CSV ต้องมีส่วนหัว `Content-Type: text/csv; charset=utf-8` และ `Content-Disposition: attachment; filename="<ชื่อไฟล์>"`
- คำขอที่มีเนื้อหาต้องเป็น JSON ที่ถูกต้อง หากเนื้อหาไม่ใช่ JSON ที่ถูกต้อง ต้องตอบ 400 `INVALID_JSON`

**เกณฑ์การตรวจรับ**

| ID | Given | When | Then |
|---|---|---|---|
| AC-COM-010.1 | ไม่มี | ส่ง `POST /api/auth/login` ด้วยเนื้อหา `{bad` | ได้ 400 `INVALID_JSON` |
| AC-COM-010.2 | ลูกค้าเรียก API ใดที่สำเร็จ | ตรวจส่วนหัว | `Content-Type` เป็น `application/json; charset=utf-8` |

### REQ-COM-011: ข้อกำหนดการแบ่งหน้า (Pagination)

Endpoint ที่คืนรายการแบบแบ่งหน้าต้องปฏิบัติดังนี้

- พารามิเตอร์ `page` เป็นจำนวนเต็มตั้งแต่ 1 ขึ้นไป ค่าเริ่มต้นคือ 1
- พารามิเตอร์ `page_size` เป็นจำนวนเต็ม 1 ถึง 50 ค่าเริ่มต้นคือ 10
- ค่าที่อยู่นอกช่วงหรือไม่ใช่จำนวนเต็มต้องได้ 400 `VALIDATION_ERROR`
- รูปแบบการตอบกลับ:
  ```json
  { "items": [ ... ], "page": 1, "page_size": 10, "total_items": 23, "total_pages": 3 }
  ```
- `total_items` คือจำนวนรายการทั้งหมดที่ตรงเงื่อนไข (ไม่ใช่จำนวนในหน้านั้น) และ `total_pages` เท่ากับ `total_items` หารด้วย `page_size` ปัดขึ้น (เป็น 0 เมื่อไม่มีรายการ)
- หน้าที่เกินหน้าสุดท้ายต้องได้ 200 พร้อม `items` เป็นอาร์เรย์ว่าง
- ผลลัพธ์ต้องเรียงลำดับแน่นอน หากเงื่อนไขการเรียงให้ค่าเท่ากัน ให้เรียงต่อด้วยรหัส (`id`) จากน้อยไปมาก เว้นแต่ข้อกำหนดของ endpoint นั้นระบุไว้เป็นอย่างอื่น

**เกณฑ์การตรวจรับ**

| ID | Given | When | Then |
|---|---|---|---|
| AC-COM-011.1 | มีสินค้าที่แสดงได้ 23 รายการ | เรียก `GET /api/products?page=3&page_size=10` | `items` มี 3 รายการ `total_items` เป็น 23 และ `total_pages` เป็น 3 |
| AC-COM-011.2 | เหมือนข้างต้น | เรียกด้วย `page_size=0` | ได้ 400 `VALIDATION_ERROR` |

### REQ-COM-012: รูปแบบวันที่ เวลา จำนวนเงิน และภาษา

- วันที่ เวลา และจำนวนเงินต้องเป็นไปตามรูปแบบที่กำหนดใน `docs/requirements/glossary.md` หัวข้อ 4 และ 5
- ข้อความ Unicode รวมถึงภาษาไทยต้องถูกจัดเก็บและส่งคืนตรงตามต้นฉบับ ไม่เปลี่ยนเป็นเครื่องหมายคำถามหรืออักขระอื่น

**เกณฑ์การตรวจรับ**

| ID | Given | When | Then |
|---|---|---|---|
| AC-COM-012.1 | ลูกค้าตั้งชื่อแสดงผลเป็น `กมล` | เรียก `GET /api/me` | `display_name` เป็น `กมล` |

### REQ-COM-013: ความสอดคล้องของข้อมูลเมื่อมีคำขอพร้อมกัน

- ข้อจำกัดความไม่ซ้ำ (unique) ที่ระบุใน `docs/design/data-model.md` ต้องถูกบังคับที่ระดับฐานข้อมูล ไม่ใช่เพียงตรวจในโปรแกรม
- เมื่อมีคำขอหลายรายการเข้ามาพร้อมกัน ระบบต้องรักษาเงื่อนไขต่อไปนี้ให้เป็นจริงเสมอ: สต็อกสินค้าไม่ติดลบ, จำนวนครั้งการใช้คูปองไม่เกินสิทธิ์ที่กำหนด, ไม่เกิดบัญชีที่มีชื่อผู้ใช้ซ้ำกัน, ไม่เกิดคำสั่งซื้อซ้ำจากตะกร้าใบเดียวกัน
- ในกรณีที่คำขอหนึ่งสำเร็จแล้ว คำขอที่เหลือซึ่งไม่อาจสำเร็จได้ต้องได้ 409 ตามรหัสที่เกี่ยวข้อง

### REQ-COM-014: ส่วนติดต่อผู้ใช้ทั่วไป

ข้อกำหนดด้านการแสดงผล การเข้าถึง (accessibility) และพฤติกรรมของหน้าจอที่ใช้ร่วมกันทุกหน้า กำหนดไว้ใน `docs/design/ui/ui-guidelines.md` และข้อความบนหน้าจอกำหนดไว้ใน `docs/design/ui/copy-deck.md` ซึ่งถือเป็นส่วนหนึ่งของข้อกำหนดนี้
