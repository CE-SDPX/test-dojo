# เครื่องมือและเคล็ดลับการทดสอบ

เอกสารนี้แนะนำวิธีใช้เครื่องมือที่จำเป็นในการทดสอบ DojoMart ได้แก่ เบราว์เซอร์ Postman curl และตัวดูฐานข้อมูล รวมถึงวิธีการเตรียมข้อมูลและบันทึกหลักฐาน

## 1. เบราว์เซอร์และ Developer Tools

เปิด Developer Tools ด้วย `F12` (หรือ `Cmd+Option+I` บน macOS)

| แท็บ | ใช้ทำอะไร |
|---|---|
| Network | ดูคำขอและผลตอบกลับของ API (รหัสสถานะ ส่วนหัว เนื้อหา) ตรวจว่าหน้าจอแสดงตรงกับที่ API ส่งมา |
| Console | ดูข้อผิดพลาดของสคริปต์บนหน้าเว็บ |
| Application → Local Storage | ดูโทเคนที่เก็บไว้ (คีย์ `dojo_token`) |
| Elements | ตรวจโครงสร้างหน้า เช่น ป้ายกำกับของช่องกรอก ข้อความทดแทนของภาพ |
| Device toolbar (`Ctrl+Shift+M`) | ทดสอบความกว้างหน้าจอ 360, 480, 768 และ 1280 px ตาม `docs/design/ui/ui-guidelines.md` |

## 2. Postman

1. นำเข้าไฟล์ `docs/design/openapi.yaml` (เมนู Import) จะได้ชุดคำขอครบทุก endpoint
2. สร้าง Environment ที่มีตัวแปร
   - `baseUrl` = `http://localhost:8001`
   - `token` (เว้นว่างไว้ก่อน)
3. ตั้งค่า Authorization ของ Collection เป็น `Bearer Token` ค่า `{{token}}`
4. ที่คำขอ `POST /api/auth/login` ใส่สคริปต์ในแท็บ Tests เพื่อเก็บโทเคนอัตโนมัติ
   ```javascript
   pm.environment.set("token", pm.response.json().token);
   ```
5. เมื่อ reset ข้อมูล โทเคนเดิมใช้ไม่ได้ ต้องเข้าสู่ระบบใหม่

Postman ไม่ได้ทำงานแบบเบราว์เซอร์ คำขอจาก Postman จึงไม่ผ่านกลไกของหน้าเว็บ เหมาะสำหรับทดสอบ API ตรง ๆ เช่น ส่งข้อมูลที่หน้าจอไม่ยอมให้ป้อน

## 3. curl

```bash
# เข้าสู่ระบบ
curl -s -X POST http://localhost:8001/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"customer1","password":"Customer123"}'

# เรียก API ที่ต้องยืนยันตัวตน (แทนที่ <token>)
curl -s http://localhost:8001/api/cart -H "Authorization: Bearer <token>"

# เพิ่มสินค้าในตะกร้า
curl -s -X POST http://localhost:8001/api/cart/items \
  -H "Authorization: Bearer <token>" -H "Content-Type: application/json" \
  -d '{"product_id":1,"quantity":2}'

# ดูรหัสสถานะอย่างเดียว
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8001/api/me
```

หมายเหตุสำหรับ Windows (PowerShell)
- ใช้ `curl.exe` แทน `curl` (เพราะ `curl` เป็นชื่อแทนของ `Invoke-WebRequest`)
- ครอบ JSON ด้วยเครื่องหมายคำพูดเดี่ยว และใช้ตัวอักษรต่อบรรทัด `` ` `` แทน `\`

## 4. การส่งคำขอพร้อมกัน

ใช้ทดสอบกรณีที่มีผู้ใช้หลายคนทำรายการเดียวกันในเวลาเดียวกัน เช่น แย่งสินค้าชิ้นสุดท้ายหรือแย่งสิทธิ์คูปอง

ตัวอย่างบน macOS/Linux (ส่ง 2 คำขอพร้อมกัน แทนที่ `<tokenA>` และ `<tokenB>` ด้วยโทเคนของผู้ใช้สองคน)

```bash
curl -s -X POST http://localhost:8001/api/orders -H "Authorization: Bearer <tokenA>" \
  -H "Content-Type: application/json" -d '{"address_id":1}' &
curl -s -X POST http://localhost:8001/api/orders -H "Authorization: Bearer <tokenB>" \
  -H "Content-Type: application/json" -d '{"address_id":2}' &
wait
```

บน Windows ใช้ Postman Runner หรือ PowerShell 7 (`ForEach-Object -Parallel`) แทนได้ ก่อนทดสอบต้องเตรียมตะกร้าของทั้งสองบัญชีให้พร้อม และ reset ข้อมูลทุกครั้งก่อนทดสอบซ้ำ

## 5. การทดสอบที่เกี่ยวกับเวลา

| ค่าที่เกี่ยวข้อง | วิธีทดสอบ |
|---|---|
| การล็อกบัญชีชั่วคราว 3 นาที | เข้าสู่ระบบผิด 5 ครั้ง แล้วรอ 3 นาที |
| อายุโทเคน 10 นาที | เข้าสู่ระบบแล้วรอ 10 นาที จึงเรียก API |
| คูปองที่กำหนดเวลาระดับนาที | ให้ `manager1` สร้างคูปองที่หมดอายุในนาทีถัดไป หรือใช้ `SOON3` ที่หมดอายุภายใน 3 นาทีหลัง reset หรือ `LATER10` ที่เริ่มใช้ได้หลัง 10 นาที |
| คำสั่งซื้อค้างชำระ 60 นาที | ใช้คำสั่งซื้อเริ่มต้นของ `customer2` (อายุ 61 และ 59 นาที) แล้วสั่งรันงานจากหน้า Jobs หรือ `POST /api/admin/jobs/cancel-unpaid-orders/run` |
| รายงานรายชั่วโมง | สร้างคำสั่งซื้อและชำระเงิน แล้วสั่งรันงาน `hourly-sales-report` โดยกำหนดช่วงเวลา `from` / `to` ที่ครอบคลุมเวลาชำระ (ละเอียดระดับนาที) |

เวลาที่ใช้คือเวลาของเครื่อง (เขตเวลา Asia/Bangkok) ตรวจนาฬิกาของเครื่องให้ถูกต้อง

## 6. การตรวจข้อมูลในฐานข้อมูล

เปิดตัวดูฐานข้อมูลตาม `getting-started.md` หัวข้อ 6 ที่ `http://localhost:8081` ตัวอย่างคำสั่ง SQL (อ่านอย่างเดียว)

```sql
SELECT id, status, grand_total_satang, created_at FROM orders ORDER BY id DESC LIMIT 10;
SELECT sku, name, stock FROM products WHERE stock <= 5;
SELECT product_id, delta, stock_after, reason, actor FROM inventory_movements ORDER BY id DESC LIMIT 20;
SELECT code, type, starts_at, expires_at FROM coupons;
```

ชื่อตารางและคอลัมน์ตามที่กำหนดใน `docs/design/data-model.md` จำนวนเงินในฐานข้อมูลเป็นหน่วยสตางค์ (หาร 100 เพื่อได้บาท) และเวลาเก็บเป็น UTC (บวก 7 ชั่วโมงเพื่อได้เวลาไทย)

## 7. แนวทางออกแบบการทดสอบ

ผู้ทดสอบควรเลือกเทคนิคที่เหมาะกับแต่ละข้อกำหนด และเขียนเหตุผลของการเลือกค่าทดสอบ

| เทคนิค | ตัวอย่างที่ใช้ได้กับระบบนี้ |
|---|---|
| Equivalence Partitioning | แบ่งกลุ่มค่าของรหัสผ่าน เบอร์โทร หมวดหมู่สินค้า |
| Boundary Value Analysis | ความยาวของชื่อผู้ใช้ จำนวนสินค้าต่อรายการ ยอดที่ทำให้เกิดส่วนลดและค่าจัดส่ง |
| Decision Table | เงื่อนไขการใช้คูปอง สิทธิ์ของแต่ละบทบาท |
| State Transition | สถานะคำสั่งซื้อ การล็อกบัญชี อายุโทเคน |
| Pairwise / Combination | ตัวกรองสินค้าร่วมกัน คูปองร่วมกับส่วนลดตามยอด |
| Exploratory Testing | ทดลองตามภารกิจ (charter) ตัวอย่างใน `exercises/charters.md` |
| API Testing | ตรวจรหัสสถานะ รูปแบบข้อผิดพลาด ความถูกต้องของข้อมูล |
| การตรวจข้อมูล | เทียบค่าที่เห็นบนหน้าจอ ใน API และในฐานข้อมูล |

คำแนะนำ
1. เริ่มจากอ่านข้อกำหนดและเกณฑ์การตรวจรับ แล้วจึงออกแบบกรณีทดสอบ ตัวอย่างในเกณฑ์การตรวจรับไม่ครอบคลุมทุกกรณี
2. ทดสอบทั้งผ่านหน้าจอและผ่าน API เพราะบางข้อกำหนดตรวจที่หน้าจอแต่ API ต้องตรวจซ้ำด้วย
3. ลองหลายบทบาทกับฟังก์ชันเดียวกัน และลองใช้โทเคนของผู้ใช้หนึ่งกับทรัพยากรของอีกคน
4. ตรวจทั้งผลที่เห็นทันทีและผลที่ตามมา (เช่น สั่งซื้อแล้วสต็อกและตะกร้าเปลี่ยนตามหรือไม่)
5. ลองลำดับขั้นตอนที่ต่างกัน (เช่น ใส่คูปองก่อนแล้วค่อยเปลี่ยนจำนวนสินค้า)
6. หากสงสัยว่าพฤติกรรมหนึ่งผิดหรือไม่ ให้ตัดสินจากเอกสาร ไม่ใช่จากความรู้สึกหรือจากระบบอื่น

## 8. ข้อมูลที่ควรบันทึกเมื่อพบข้อบกพร่อง

กติกาและแบบฟอร์มการรายงานเป็นไปตามระบบรายงานที่ผู้สอนกำหนด อย่างน้อยควรมีข้อมูลต่อไปนี้เพื่อให้ผู้อื่นทำซ้ำได้

| รายการ | รายละเอียด |
|---|---|
| เวอร์ชัน | `version` และ `source_hash` จาก `GET /api/version` |
| สภาพแวดล้อม | เบราว์เซอร์และรุ่น ความกว้างหน้าจอ (เมื่อเกี่ยวกับการแสดงผล) |
| ข้อมูลเริ่มต้น | ยืนยันว่า reset ก่อนเริ่ม และระบุบัญชีที่ใช้ |
| ขั้นตอน | ทีละขั้นที่ทำซ้ำได้ ระบุข้อมูลที่ป้อนตรง ๆ |
| ผลที่คาดหวัง | อ้างรหัสข้อกำหนดหรือเกณฑ์การตรวจรับ (เช่น `REQ-CART-006`, `AC-COUP-002.1`) หรือเอกสารออกแบบที่เกี่ยวข้อง |
| ผลที่เกิดขึ้นจริง | ข้อความ รหัสสถานะ ตัวเลข |
| หลักฐาน | ภาพหน้าจอ เนื้อหาคำขอและคำตอบของ API |
